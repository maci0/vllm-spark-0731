# 06-6. Qwen3.8-27B

전체 선택 기준은 [DGX Spark에서 돌릴 모델 선택](06-4-model-selection.md)에서 확인할 수 있습니다.

기준일: **2026-08-22**

## 한 줄 결론

Qwen3.8-27B는 단일 Spark에서 코드·UI·JSON worker로 시작하기 좋은 후보다. 다만 Qwen3.8이라는 모델 이름과 runtime 로그의 `Qwen3_5ForConditionalGeneration` architecture 표시는 함께 성립할 수 있으므로, model id·config·weight revision을 확인한 뒤 parser와 speculative decoding을 검증해야 한다.

## 실행 프로필

| 항목 | 현재 원고의 판정 |
|---|---|
| 단일 Spark | NVFP4·FP8·SGLang/vLLM speculative community recipe가 있음 |
| 두 대 Spark | TP=2 또는 두 endpoint 구성 사례가 있음 |
| 주요 작업 | 코드, UI·CSS, JSON, 짧은 tool call, 일부 vision 경로 |
| 직접 검증 상태 | OBLITERATED 파생 모델의 기능 smoke test와 recipe 조사를 구분하며, 원본 종합 품질 benchmark로 해석하지 않음 |
| 수치 해석 | SGLang·vLLM·Ollama·GGUF 결과의 runtime과 workload를 분리 |

이 페이지는 실행 선택을 위한 요약 프로필이다. 커뮤니티가 만든 serving과 에이전트 활용 사례는 [06-12](06-12-qwen38-community-builds.md), 공통 선택 기준은 [06-4](06-4-model-selection.md)에서 확인한다.

## 3분 이해 (ELI5) — 모델 카드

Qwen3.8은 빠른 코드·UI worker 후보다.

```text
작은 역할을 빠르게 반복 → router가 작업을 배분
architecture 로그 확인   → 모델 id와 runtime을 함께 검증
```

단일 Spark에서 시작하기 쉽다는 말이 원본 품질과 모든 recipe의 성공을 보장하지는 않는다.

Qwen3.8-27B는 단일 Spark에서 시작하기 좋은 모델이다. DeepSeek처럼 거대한 MoE weight를 두 노드에 나누는 모델은 아니지만, dense 27B라서 모든 token에서 많은 weight를 읽는다. 그래서 기본 decode보다 NVFP4·FP8·MTP·DSpark·DFlash2 조합이 결과를 크게 바꾼다.

## 공식 모델 카드에서 확인한 것

[Qwen3.8-27B model card](https://huggingface.co/Qwen/Qwen3.8-27B)는 다음을 명시한다.

- 27B causal language model with vision encoder
- native multimodal: image와 video 이해
- native context 262,144, YaRN으로 최대 1,000,000 확장
- thinking은 기본 활성화이며 request에서 끌 수 있고, `reasoning_effort`를 조절할 수 있음
- MTP를 학습함
- Transformers·vLLM·SGLang·TokenSpeed 호환 artifact
- Apache 2.0 라이선스 표시

model card는 Qwen3.8이 Qwen3.5 아키텍처 기반이라고 설명한다. 따라서 vLLM config나 로그에 `Qwen3_5ForConditionalGeneration`이 나타나는 것은 모델 이름이 Qwen3.5로 바뀌었다는 뜻이 아니다. `model id`, `config.json`, weight revision을 함께 확인한다.

## 단일 Spark recipe

[MiaAI-Lab SGLang recipe](https://github.com/MiaAI-Lab/Qwen3.8-27B-SGLang-DGX-Spark)는 NVFP4 W4A4, FP8, BF16과 MTP/DSpark/DFlash2 경로를 다룬다. 커뮤니티 자료에는 대략 다음 범위가 보고된다.

| 경로 | 보고된 성격 | 주의 |
|---|---|---|
| SGLang NVFP4 + DFlash/DSpark | 약 34~38 tok/s 단일 작업 사례 | prompt·draft·container memory cap에 의존 |
| vLLM + MTP/FP8 | 약 20~30 tok/s대 사례 | version·parser·concurrency를 고정 |
| 4-bit/GGUF + speculative | 더 높은 단일 decode 주장도 있음 | quality와 long context를 별도로 확인 |
| Ollama Q4_K_M | 약 11.5~11.8 tok/s 현장 사례 | 빠른 SGLang 결과와 같은 표에 합치지 않음 |

Qwen3.8의 실전 최적화는 “양자화가 작을수록 무조건 빠르다”가 아니다. draft acceptance, KV dtype, context, CPU pinning, CUDA graph, concurrent requests가 함께 속도를 결정한다.

## 1대와 2대의 역할

| Spark 수 | 현실적인 구성 | 주 용도 |
|---:|---|---|
| 1 | NVFP4/FP8 + SGLang/vLLM speculative | coding worker, UI·CSS, JSON, 짧은 tool |
| 2 | TP=2 direct QSFP/RoCE | 더 긴 context 또는 single endpoint |
| 2 | DP/endpoint 두 개 | 여러 agent와 동시성 |
| 3 | TP=2 + worker 1대 | DeepSeek supervisor와 역할 분리 |
| 4 | Qwen TP=2 + DeepSeek TP=2 | 2×2 독립 endpoint |

[NVIDIA Forum의 듀얼 vLLM+MTP 측정](https://forums.developer.nvidia.com/t/qwen3-8-27b-on-dual-sparks/380350)은 단일 요청과 aggregate가 다른 최적점을 보였다. 다른 [SGLang+DFlash2 측정](https://forums.developer.nvidia.com/t/qwen3-8-27b-nvfp4-on-single-dual-dgx-spark-sglang-dflash2-fully-openai-compatible/380732)은 code와 prose에서 1대→2대의 변화가 달랐다. 이 수치들은 같은 공식 benchmark가 아니므로 증가율만 일반화하지 않는다.

## Tool parser와 에이전트

Qwen3.8은 coding worker로 쓰기 좋지만 endpoint를 띄운 순간 agent-ready가 되는 것은 아니다.

- `qwen3` reasoning parser와 `qwen3_coder` tool parser를 용도에 맞게 선택한다.
- tool schema에서 arguments가 JSON으로 유지되는지 확인한다.
- thinking off/on이 tool call 형식을 바꾸는지 확인한다.
- tool 오류 후 다음 turn에서 같은 호출을 반복하지 않는지 확인한다.
- Claude Code·Qwen Code·OpenCode·Hermes 등 client마다 message block 변환을 점검한다.

현재 저장소의 `OBLITERATUS/Qwen3.8-27B-OBLITERATED` BF16 테스트는 원본 Qwen3.8과 구별한다. models endpoint, 한국어·코드·JSON·thinking·긴 context·동시 요청을 확인한 것은 기능 smoke test이며, 원본 모델의 종합 품질 benchmark가 아니다.

## Vision의 경계

공식 카드는 native image/video를 말하지만, 사용 중인 checkpoint와 runtime이 vision encoder를 실제로 로드했는지 확인해야 한다. 텍스트 전용 quant, OBLITERATED 파생, parser-only server에서는 이미지 요청이 실패하거나 다른 경로로 떨어질 수 있다.

vision을 기록할 때는 다음을 분리한다.

```text
text endpoint
vision encoder loaded
single image
document/OCR
screen coordinate
video frame
tool call after vision
```

## Qwen3.8을 선택할 때

Qwen3.8은 다음 조건에서 첫 후보로 삼는다.

- 한 대에서 coding·UI·JSON worker가 필요하다.
- 여러 짧은 요청의 aggregate throughput이 중요하다.
- speculative decoding을 조정할 수 있다.
- native vision을 별도 검증할 계획이 있다.

DeepSeek가 긴 context supervisor라면 Qwen3.8을 worker로 두는 역할 분리는 자연스럽다. 단, 두 모델을 한 대에 모두 넣는 것이 아니라 endpoint와 메모리 profile을 분리하는 것이 기본이다.

## 체크리스트

- [ ] 원본 Qwen3.8과 파생 checkpoint를 구분했다.
- [ ] config의 `Qwen3_5...` architecture를 모델 오인식으로 판정하지 않았다.
- [ ] NVFP4·FP8·4-bit·GGUF를 같은 benchmark 표에 합치지 않았다.
- [ ] c1 decode와 c4/c8 aggregate를 분리했다.
- [ ] native vision과 text-only quant를 구분했다.
- [ ] tool parser와 실제 agent loop를 따로 통과시켰다.
