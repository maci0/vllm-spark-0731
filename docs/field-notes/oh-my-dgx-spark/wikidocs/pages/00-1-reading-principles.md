# 00-1. 결과 상태·증거 등급·업데이트 원칙

상태: Wikidocs GitHub 연동 배포판

기준일: **2026-08-23**

이 책은 DGX Spark 사용 설명서와 모델 목록을 한데 모은 책이 아니다. 독자가 먼저 **무엇을 궁금해하는지 고르고**, 그 질문에 필요한 장만 읽은 뒤, 자신의 장비에서 직접 확인할 수 있도록 만든 결정서·recipe·실험 노트다.

가장 먼저 답할 질문은 네 가지다.

1. 이 장비가 내 작업에 맞는가?
2. 128GB 안에서 어떤 모델과 context를 감당할 수 있는가?
3. 인터넷에서 본 수치가 어떤 조건의 결과인가?
4. “실행됐다”를 넘어 실제 API·tool·에이전트로 쓸 수 있는가?

공식 사양, 실행 가능한 GitHub recipe, 포럼·Reddit·X의 사용담, 이 저장소의 직접 실측은 서로 다른 증거로 기록한다.

## 이 책은 세 가지 문서다

| 문서 | 독자가 얻는 것 | 주로 읽을 장 |
|---|---|---|
| 결정서 | Spark가 내 작업과 예산에 맞는지 판단 | 01·02·12·14 |
| recipe | 부팅부터 서버와 모델까지 실행 | 03·04·05·06·08 |
| 실험 노트 | 수치·실패·출처·재현 여부 확인 | 07·15·16·19 |

## 3분 이해 (ELI5)

이 책은 모델을 “올렸는가”만 보는 책이 아니다. 자동차로 비유하면, 시동이 걸리는지(`loaded`), 도로를 달리는지(`serves`), 속도를 재는지(`benchmarked`), 목적지까지 안전하게 가는지(`agent-tested`)를 따로 확인한다.

```text
모델 파일 → 서버 응답 → 속도 측정 → 도구 호출 → 실제 작업
```

숫자를 볼 때는 “무엇을 측정한 숫자인가?”를 먼저 확인한다.

## 먼저 질문을 고른다

책의 결론은 장비와 작업에 따라 달라진다. 다음 표에서 자신의 질문을 고르면 된다.

| 지금 궁금한 것 | 읽을 순서 | 먼저 확인할 질문 |
|---|---|---|
| 사기 전에 판단하고 싶은 경우 | 01장 → 02장 → 10-1 | capacity와 속도 중 무엇이 필요한가? |
| 첫날에 서버까지 올리고 싶은 경우 | 03-1 → 03-4 → 05-1 | 내 장비가 정상이고, 모델이 실제로 응답하는가? |
| 모델을 고르고 싶은 경우 | 01장 → 06-4 → 해당 모델 서브챕터 | 내 작업·context·노드 수에 맞는 후보는 무엇인가? |
| 숫자가 왜 사람마다 다른지 알고 싶은 경우 | 02장 → 05-1 → 부록 B | 같은 모델·prompt·runtime 조건인가? |
| 에이전트를 운영하고 싶은 경우 | 03-4 → 08-1 → 09-1 | tool loop와 오류 복구가 되는가? |
| 여러 대를 연결하고 싶은 경우 | 02장 → 07-1 → 07-4 | 메모리보다 링크와 통신이 먼저 막히지 않는가? |
| 커뮤니티 결과를 검토하는 경우 | 10-4 → 06-9 또는 06-12 → 부록 B | 주장·조건·직접 재현을 분리했는가? |

이 책에서 모델 선택 장은 “무엇을 고를지”를 정하고, 실행 장은 “어떻게 띄울지”를 설명하며, benchmark 장은 “어떻게 믿을지”를 정한다. 이 세 질문을 한 문장이나 한 숫자로 합치지 않는다.

## 다섯 단계로 읽는다

```text
질문 고르기 → 장비 적합성 판단 → 환경 고정 → 첫 모델 증명 → 측정·운영
```

처음부터 06-4의 모델 목록으로 뛰어들지 않는다. 모델 이름을 먼저 고르면 메모리·context·엔진·도구 조건을 뒤늦게 맞추느라 실패 원인을 잃기 쉽다.

## 0.1 결과의 상태를 나눈다

책에서 다음 표현은 같은 뜻으로 사용하지 않는다.

| 표현 | 의미 |
|---|---|
| loaded | weight와 runtime이 메모리에 올라감 |
| generates | 한 번의 생성 요청에 답함 |
| serves | API endpoint가 기동되고 health 요청에 응답함 |
| benchmarked | 고정된 조건과 측정 방법으로 속도를 기록함 |
| tool-tested | parser, schema, 함수 이름과 arguments를 검증함 |
| agent-tested | 여러 단계의 도구 호출, 오류 복구와 종료 조건까지 확인함 |

모델 카드의 “지원”은 대개 기능 설명이다. 그것만으로 이 장비에서 `serves`, `benchmarked`, `agent-tested` 상태가 되지는 않는다.

## 0.2 성능 숫자를 읽는 법

`tok/s`에는 최소 네 가지가 있다.

- prefill: 입력을 KV cache로 처리하는 속도
- decode: 이미 처리한 입력 뒤에 출력을 생성하는 속도
- end-to-end: HTTP, prefill, decode, 종료 처리를 모두 포함한 속도
- aggregate: 여러 요청의 출력 속도를 합친 값

단일 사용자의 decode와 네 개 요청의 aggregate를 같은 순위표에 놓지 않는다. 긴 입력에서는 prompt 초반의 prefill peak와 전체 요청의 실효 prefill도 달라진다.

## 0.3 증거 등급

| 등급 | 자료 | 책에서 쓰는 방법 |
|---|---|---|
| A | NVIDIA·DeepSeek·OpenAI 공식 문서, 모델 카드, 논문 | 사양과 평가 방법의 원문 |
| B | 실행 명령과 revision이 공개된 GitHub recipe | 재현 후보. 우리 장비에서 다시 확인 |
| C | 로그와 조건이 있는 커뮤니티 benchmark | 범위와 실패 패턴의 근거 |
| D | X, Reddit, 포럼, 아카라이브, 서버포럼 사용담 | 실험 주제와 운영 문제를 찾는 자료 |
| L | 이 저장소의 로컬 실측 | 장비·날짜·image에 한정된 직접 증거 |

출처 등급이 높다고 실측이 자동으로 맞는 것은 아니다. 반대로 D 자료도 반복해서 같은 장애를 보여주면 중요한 검증 출발점이 될 수 있다.

## 0.4 명령을 실행할 때

각 실험은 다음 정보를 함께 남긴다.

```text
date / host / OS / driver / CUDA / runtime / image digest
model revision / tokenizer / quant / KV dtype
context / max output / thinking or reasoning effort
speculative decoding / concurrency / prompt fixture
TTFT / prefill / decode / aggregate / error rate
```

문서에 명령을 적을 때는 로컬에서 통과한 명령과 실험용 명령을 구분한다. 실행하지 않은 명령은 `실험용`이라고 표시한다.

## 0.5 이 책의 업데이트 방식

DGX Spark runtime과 모델 recipe는 빠르게 바뀐다. 따라서 숫자를 고칠 때 문장만 바꾸지 않고 다음을 함께 수정한다.

1. 원문 링크와 출처 등급
2. 모델·runtime·image revision
3. 측정 조건과 raw 결과
4. 이 장의 결론과 아직 모르는 것

최신 원고는 비공개 [WikiDocs 배포 저장소](https://github.com/recrack/oh-my-dgx-spark-wikidocs)의 bundle을 기준으로 연결되어 있다. `recrack/oh-my-dgx-spark-wikidocs`에 push하면 등록된 webhook을 통해 Wikidocs 책에 자동 동기화된다. Wikidocs GitHub 연동은 `README.md`를 책 소개로, `TOC.md`를 목차로, `pages/` 파일을 본문으로 사용한다.

## 이 장의 체크리스트

- [ ] 이 숫자가 loaded, serves, benchmarked 중 어느 상태인지 적었다.
- [ ] prefill, decode, end-to-end, aggregate를 구분했다.
- [ ] 모델과 runtime의 revision을 기록했다.
- [ ] 공식 주장과 로컬 실측을 같은 표의 동일한 값처럼 합치지 않았다.
- [ ] 실행하지 않은 명령을 검증 완료로 쓰지 않았다.
